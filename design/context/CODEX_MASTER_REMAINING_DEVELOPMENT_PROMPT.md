# Phase 0 — Redesign Difficulty Around Actual Puzzle Solving

## Non-negotiable player finding

A real player has manually played the current early campaign and reports that almost every level feels easy, there is no convincing difficulty increase, and many boards feel mostly empty. Treat this as a product defect, not a request to relabel existing scores.

Do not start Level 151 until this phase is complete. The generator, solver analysis, acceptance gates, and existing Levels 1–150 must first be reviewed and remediated. If the repository uses zero-based display/internal numbering, map the ranges explicitly; do not accidentally create or delete a level because the attached feedback called the first range `0–100`.

## Inspect before editing

Trace the complete current pipeline from authored/generated candidate through validation, solving, difficulty/quality scoring, certification, serialization, and runtime loading. Determine:

- Why levels can be valid and solver-certified yet strategically trivial.
- Whether the solver records only a solution or explores the decision tree.
- Whether Difficulty v2 overweights object count, density, board size, or minimum move count.
- Whether visually different boards are logically equivalent.
- Whether magnets, walls, empty space, and alternative moves materially affect the solution.
- Whether early exits, forced moves, wide-safe solution sets, or shallow dependencies dominate Levels 1–150.
- Which existing engine, solver, analyzer, and generator components can be reused safely.

Write the diagnosis to `docs/development/DIFFICULTY_REDESIGN_DIAGNOSIS.md` before changing the scoring or campaign. Include evidence from actual current level metrics; do not guess and do not blindly rewrite unrelated gameplay code.

## Gameplay-authoritative search analysis

Use the production `:game-core` transition rules. Extend or refactor the deterministic solver so it can report, with documented caps and truncation flags:

1. Solvability and minimum solution length.
2. Legal actions at each explored state.
3. Meaningful decision points: states with multiple plausible actions whose outcomes are strategically different.
4. Effective branching factor, not merely the raw number of tappable arrows.
5. Dead-end actions/states and the depth at which failure becomes provable.
6. Shortest dependency-chain depth and multi-stage interaction depth.
7. Number of shortest solutions and a bounded estimate/count of viable solution families.
8. Forced-move ratio and obvious-next-action ratio.
9. Search effort using stable measures such as unique states expanded, depth distribution, and backtracking pressure.
10. Meaningful constraint contribution from magnets, polarity, occlusion, cancellation, walls, and routes.
11. Meaningful versus unused empty cells.

A plausible action must be defined from information available to a player, not from solver foreknowledge. A dead end is valuable only when the player could logically distinguish it; arbitrary guess traps reduce Quality even if they increase search effort.

## Difficulty model v3

Create a versioned, normalized `0..100` Puzzle Difficulty v3 based on actual search and solution structure. It must combine documented, normalized components such as:

- solution complexity;
- meaningful decision complexity;
- effective branching complexity;
- dependency depth;
- fair dead-end/backtracking complexity;
- solution constraint/alternative-solution complexity;
- mechanic interaction complexity;
- meaningful spatial/routing complexity.

Do not use an arbitrary uncalibrated sum. Document raw metric definitions, normalization bounds, caps, weights, interactions, confidence, truncation handling, and calibration fixtures in `docs/development/DIFFICULTY_V3_SPEC.md`.

Object count, obstacle count, density, grid size, and solution length may be supporting signals only. They must not independently make a level Hard. A visually busy puzzle with one obvious action at every state must score Easy.

Keep Difficulty and Quality separate. Difficulty estimates cognitive/search burden; Quality penalizes unfair guessing, irrelevant objects, accidental clutter, excessive ambiguity, tedious repetition, unreadability, and fragile/truncated analysis.

## Hard-band rejection gates

Add explicit band-aware acceptance rules in addition to the numeric score. A candidate aimed at a high band must be rejected when its structure is strategically trivial—for example, one meaningful action at nearly every state, a very short/forced solution, no dependency chain, no consequential branch, or several obvious safe solutions—even if its object count or weighted score appears high.

Likewise, reject an early/tutorial candidate that has extreme ambiguity or complexity. Rejection reasons must be machine-readable and appear in diagnostics.

At minimum, later Hard and Very Hard campaign bands require independently configured floors for:

- meaningful decision points;
- dependency depth;
- effective branch diversity;
- solution constraint;
- non-forced portion of the solution;
- mechanic relevance.

Do not force every level to have one unique solution or a dead end. Use varied logical structures: correct order, sequential dependency, limited safe actions, routing, magnet interaction chains, multi-stage solutions, cancellation/occlusion reasoning, and recoverable false paths.

## Density and purposeful space

Reduce large amounts of unused empty space without using random clutter. Analyze whether a cell/object participates in a legal route, line of sight, blocking relationship, choice, dependency, or alternate branch. Report purposeful occupancy separately from raw occupancy.

Use approximate calibration guidance for the first 100 displayed campaign levels:

| Displayed range | Target difficulty | Purpose | Approximate empty space |
|---|---:|---|---:|
| 1–10 | 5–15 | Tutorial and immediate comprehension | 60–75% |
| 11–25 | 15–30 | Easy, but requires thought | 45–60% |
| 26–40 | 30–45 | Planning introduction | 30–45% |
| 41–60 | 45–60 | Genuine medium decisions | 30–45% |
| 61–80 | 60–75 | Hard, frequent reconsideration | 20–35% |
| 81–100 | 75–90 | Genuinely challenging | 20–35% |

These are calibration bands, not permission to manufacture a score or fill cells. Allow local difficulty variation while preserving a clear rising trend.

For Levels 101–150, continue from the established upper bands with deliberate recovery levels and peaks; do not reset difficulty after Level 100.

## Remediate Levels 1–150

Evaluate every existing level with Difficulty v3. Preserve the exact level count and stable level IDs. Classify each level as `KEEP`, `TUNE`, or `REPLACE`, with reasons.

- Preserve good tutorial levels where appropriate.
- Tune or replace strategically trivial mid/late levels.
- Re-certify every changed level using the production engine.
- Update expected content fingerprints through an explicit versioned content migration.
- Preserve player progress, stars, best records, rewards, unlocks, and economy by stable level ID. Never wipe progress merely because a board changed.
- Document the product decision for previously earned best records if a changed board makes those records incomparable; prefer preserving user-earned value while versioning future records.
- Do not claim a generated replacement is handcrafted.

Generate an oversized deterministic candidate pool offline/build-time, then accept only candidates inside the target band that pass solver, Quality, mechanic-relevance, diversity, and readability gates. Expensive exhaustive work must never run during ordinary gameplay.

## Structural diversity

Extend duplicate/similarity analysis beyond geometric fingerprints where practical. Detect levels that differ visually but share substantially the same dependency graph, legal-action progression, solution shape, mechanic roles, or route structure. Penalize repetitive clusters and report any accepted near-neighbor with justification.

## Required diagnostics

Produce machine-readable and human-readable reports for all Levels 1–150 containing at least:

- level ID and content version;
- grid size and purposeful occupancy/empty-space ratios;
- arrow, magnet, wall, and other relevant counts;
- Difficulty v3 total, component scores, confidence, and target band;
- minimum solution length;
- meaningful decision points;
- effective branching factor;
- forced-move ratio;
- dead-end actions/states and fair-dead-end assessment;
- dependency depth;
- shortest-solution count/solution-family estimate;
- unique states expanded and truncation status;
- mechanic relevance;
- Quality score/reasons;
- structural-similarity cluster;
- origin and `KEEP`/`TUNE`/`REPLACE` decision;
- manual-review status.

Include a summary table for ranges 1–10, 11–25, 26–40, 41–60, 61–80, 81–100, 101–125, and 126–150 with averages and distributions. Do not hide outliers behind averages.

## Tests and phase gate

Add golden solver fixtures for solvable/unsolvable puzzles, minimum solutions, meaningful branching, forced sequences, fair dead ends, dependency chains, multiple solutions, search caps, and deterministic replay. Add Difficulty v3 fixtures demonstrating that a logically complex sparse puzzle can outrank a busy forced puzzle.

Add progression tests using band medians/percentiles rather than only checking four individual levels. Small local dips are allowed for pacing, but the overall trend must be unmistakable. Include explicit rejection tests proving that a nominal difficulty-70 candidate with trivial decisions cannot pass.

Phase 0 is `COMPLETE` only when:

1. All 150 levels are schema-valid, solvable, replay-certified, and unique under required duplicate checks.
2. The target bands are met or every exception is individually justified and manually approved.
3. Levels 41–60 contain genuine decisions, 61–80 regularly require planning/reconsideration, and 81–100 meet the Very Hard structural floors.
4. A reviewer checklist is generated for human playtesting of at least representative levels from every band and all Hard/Very Hard outliers. Do not fabricate human results.
5. Difficulty comes from logical order, interaction, dependency, and constrained choices—not random clutter or inflated board size.
6. Existing player data survives migrations.
7. The diagnosis, v3 specification, per-level report, distribution report, remediation manifest, migration report, and remaining limitations are checked in.

If actual human playtesting is unavailable, mark that verification as pending, but do not weaken automated structural gates. Phase 1 may proceed only when code/content gates pass and the absence of human validation is clearly recorded rather than falsely claimed.

# Phase 2 — New Mechanic Prototype: Insulator

## Product rule

Add exactly one new mechanic: **Insulator**.

An Insulator is a static, non-colliding board object that blocks magnetic line of sight but does not block arrow movement.

Frozen proposed rule contract:

1. An Insulator has a stable ID and cell position.
2. It cannot share an authored cell with an arrow, magnet, wall, or another Insulator.
3. When determining visible aligned candidate magnets, an Insulator strictly between the arrow and magnet blocks that magnet’s influence.
4. An arrow tracing through an Insulator cell continues normally; the Insulator is not a collision target.
5. An Insulator never attracts, repels, captures, flips, moves, activates, or changes state.
6. It does not alter equal-distance cancellation except by hiding a candidate magnet.
7. It does not create a new player action.
8. It remains on the board after every move.

If this creates a material contradiction with existing rules, document it and stop before silently changing semantics.

## Engine/schema

- Version the rules and level schema while retaining full backward compatibility for Levels 1–200.
- Add immutable Insulator domain/DTO support.
- Update occupancy validation, line-of-sight resolver, route tracing, state identity only where rule-relevant, serialization, fingerprints, transforms, solver, generator, diagnostics, and reports.
- Do not add animation state to core models.
- Solver must call the production engine; no duplicate Insulator logic.

## Resolution output

Expose rule-owned diagnostic evidence for magnet visibility blocked by an Insulator, without making UI reconstruct visibility. Insulator cells traversed by arrows may appear in route data normally.

## Visual/accessibility

- Use a neutral slate/white geometric isolator or split-shield symbol, distinct from walls and magnets.
- Do not introduce an unrelated neon color or emoji.
- Communicate “blocks field, not arrow” through shape, tutorial copy, field truncation, and accessible description.
- Maintain high contrast and reduced-motion support.

Tutorial copy:

> Insulators block magnetic fields, but arrows pass through them.

## Prototype content

Create 20 experimental, checked-in, solver-certified prototype levels outside the numbered campaign:

- 1–5: direct line-of-sight blocking
- 6–10: arrow passes through Insulator
- 11–15: Insulator changes controlling magnet or cancellation
- 16–20: Insulator combined with polarity/order/occlusion

They must not affect campaign progress, stars, coins, Daily generation, or analytics funnels yet.

## Metrics/generation

Extend Difficulty v3/Quality with Insulator dependency/relevance metrics. Reject levels where Insulators are decorative and do not affect any certified or meaningful counterfactual action.

## Gate

- All old levels retain identical engine results, fingerprints, and certified solutions.
- All 20 prototype levels solve/replay and pass quality/uniqueness/readability gates.
- Golden tests cover blocked influence, pass-through, controller change, cancellation, collision non-effect, and backward compatibility.
- Produce `docs/mechanics/INSULATOR_RULES_V1.md`, implementation report, prototype catalog, and review checklist.

Do not promote Insulator into the numbered campaign until Phase 2 is `COMPLETE`.

# Phase 6 — Infinite Mode

## Product boundary

Infinite Mode is a separate offline mode that produces deterministic, solver-certified puzzles after the campaign architecture is mature. It does not create Level 301 or alter numbered progression.

## Unlock and modes

- Unlock Infinite Mode after a configurable campaign milestone, default Level 100 completion, without blocking campaign play.
- Initial difficulty choices: `Relaxed`, `Balanced`, `Challenging`, `Expert`.
- Adaptive selection is not implemented until Phase 7.

## Identity and determinism

Define:

```text
infinitePuzzleId = generatorVersion + profile + seed + contentHash
```

- Use a stable explicit PRNG and stable hash; never platform `hashCode()`.
- Same inputs produce identical canonical content across supported devices.
- Store seed/profile/generator/schema/rules/analyzer versions and fingerprint.
- Allow issue reproduction from puzzle ID without exposing device/user identifiers.

## Generation/certification

- Run off the main thread and support cancellation.
- Enforce attempt, solver-state, wall-clock, and memory caps.
- Use approved mechanics and board sizes only.
- Validate schema, solve with production solver, replay solution, score Difficulty/Quality, and reject duplicates against recent history.
- Never present an uncertified candidate.
- If generation fails, use a bundled certified fallback bank matched to difficulty/mechanics.

## Local history

Persist a bounded versioned history:

- Puzzle ID/seed/profile/fingerprint
- Started/completed state
- Best stars/actions/overloads/hints if stars are used
- Recent fingerprints for duplicate avoidance
- Favorite/bookmark state only if useful and bounded

Do not store full unlimited histories. Define migration and eviction.

## Economy

Initial Infinite Mode grants no repeatable coins and does not affect campaign unlocks. Completion may record score/streak statistics only. Phase 8 may add bounded rewards after economy simulation.

## UI/accessibility

- Separate Infinite entry on Home after unlock
- Difficulty selector with explanations
- Generation progress with cancel and bounded timeout
- Puzzle ID in diagnostics
- Replay/new puzzle controls
- Offline messaging and fallback transparency
- Full TalkBack, large text, high contrast, reduced motion, and path-preview support

## Tests/gates

- Deterministic seed golden vectors
- All profiles generate/certify within caps for representative seed suites
- Fallback on failure/timeout
- No duplicate recent fingerprints
- Process restart/cache/history migration
- No campaign/economy mutation
- UI cancellation and accessibility
- Performance on lower-end device/emulator where available

Produce `docs/infinite/INFINITE_MODE_SPEC.md`, generator benchmark, fallback-bank report, seed contract, persistence/migration, and QA report.

## Current-source requirement

Record exact official URLs, access date, resolved SDK version, purchase-processing rules, pending-purchase behavior, acknowledgement deadlines, and testing guidance in `docs/monetization/BILLING_REQUIREMENTS.md`.

## Remove Ads product

Use a production product ID supplied/configured by the owner; use a non-production placeholder only in safe development configuration. Never invent a live product.

Entitlement removes:

- Campaign interstitials
- Any future non-rewarded ads

It does not remove voluntary rewarded choices; users may still choose them. Make this clear.

## Billing architecture

- Wrap Play Billing behind `BillingService`/repository interfaces with fake/no-op implementations.
- Query product details and owned purchases through current APIs.
- Grant only when purchase state is `PURCHASED`, never `PENDING`.
- Handle cancellation, pending completion, already-owned, disconnect/reconnect, app foreground/query, restore on reinstall/device using Play ownership, and duplicate callbacks.
- Acknowledge non-consumable purchase within required window after entitlement grant.
- Keep processing idempotent by purchase token/product, without logging raw tokens.
- Never hold Activity references.
- Hide/disable purchase UI when Play Billing is unavailable.

Official guidance recommends secure backend verification. This project is intentionally backend-free; document that client-only entitlement verification is less fraud-resistant. Do not pretend server verification exists. If the security/owner risk is unacceptable, keep Billing behind a disabled development flag and mark the phase partially blocked rather than fabricating safety.

## Rewarded coins

Add one explicit optional placement:

> Watch an ad for 60 coins

- Maximum 3 rewarded coin grants per local day.
- Reward only from the SDK reward callback.
- Atomic, idempotent transaction with unique local ID.

- No grant on early dismissal.
- Hidden/unavailable gracefully offline, consent-blocked, capped, or not loaded.
- Do not auto-play or pressure after insufficient coins.
- Keep the existing rewarded-hint path/caps unchanged.
- Simulate economy impact before enabling by default.

## Infinite rewards

After simulation, Infinite completion may grant a small bounded first-completion reward, but only if the combined system cannot be farmed indefinitely. Preferred default: no automatic Infinite coins; rewarded coin ads remain optional. Any change requires versioned economy config and simulation report.
